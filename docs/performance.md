# 性能与架构现状（实测）

这份文档记录**实测数据**，不是设计意图。写它的原因：优化最怕两件事——
凭感觉改（改错地方）、改完没人知道（下一个人重新排查一遍）。

所有数字来自本机实测（190 会话 / 23 万条消息 / Windows + Python 3.14）。

## 接口耗时（冷缓存）

| 接口 | 耗时 | 说明 |
|------|------|------|
| `/api/status` | 4 ms | |
| `/api/sessions` | 3 ms | |
| `/api/messages`（60 条） | 7 ms | |
| `/api/contacts`（100 条） | 8 ms | |
| `/api/stats/contacts` | 24 ms | |
| `/api/profile`（单会话） | 222 ms | 逐条解压 + 情感打分 |
| `/api/moments` | 558 ms | 首次要解析 sns.db 全量 |
| `/api/stats/global` | 320 ms | |
| **`/api/report`** | **3.9 s** | 唯一超过 1 秒的接口 |

首屏导航可见 0.34 s，切页 0.2 s（前端不是瓶颈）。

## 年报为什么慢，以及做到了什么程度

profile 结论：`jieba.cut` 占 3.47 s（72%），25 万次调用。
聊天消息中位长度只有 11 字，**每条 `cut()` 的固定开销占比极高**。

三处优化（都是无损的，见下）：

| 改动 | 效果 |
|------|------|
| 批量分词（换行拼接后一次 cut） | 2.37 s → 1.53 s |
| `_texts` 只解压不解析（纯文本跳过 protobuf/XML） | 0.92 s → 0.44 s |
| 结果缓存（带数据集签名） | 重复访问 5.9 s → **0.003 s** |

**首次仍需约 5 秒**，这是 jieba 词典匹配的固有成本，无损优化已到边界。
界面据此改成「说明在算什么 + 约多久 + 结果会缓存」，而不是干等两个灰块。

### 试过但**没有**采用的方案

- **丢弃 ≤3 字的短消息**：能提速 2.1 倍，但会丢掉「明白」（53 次）这类词，
  且让「哈哈哈」从 103 掉到 71。**这是统计口径的改变，不能偷偷做**。
- **jieba 并行模式**：Windows 上不支持。
- **lru_cache**：只看参数不看数据，导入新记录后会返回过期结果。

## 缓存为什么带数据集签名

`functools.lru_cache` 在这里是错的：用户反复开关 GUI、反复重新解密，
数据变化是常态。参数没变、数据变了，lru_cache 会返回**过期统计**——
用户会以为工具算错了，且没有任何报错提示。

签名只算「哪些表 / 各多少条 / 最新时间」，实测 **0.2 ms**。
不能为了判断能否复用而先花掉一半计算。

拿不到索引时返回每次不同的值：**宁可缓存不命中，也不能命中错的数据**。

## 无损性是怎么验证的

优化最容易造成「结果悄悄变了但没人发现」。所以每处改动都与旧实现逐项对比：

- `_texts`：新旧文本集 **3274 条 == 3274 条**，逐条一致
- `extract_keywords`：新旧词表**前 100 项与计数完全一致**
- 缓存：消融实验（绕过缓存 5.92 s vs 走缓存 0.000 s）证明它真的在起作用

## 数据库

用的是微信自己的表结构与索引，**不额外建索引**：

- 163 张 `Msg_<md5>` 表（每会话一张），已带 `TYPE_SEQ` / `SORTSEQ` /
  `SERVERID` / `SENDERID` 四个索引
- 搜索走 `(local_type & 4294967295) IN (1, 49)` 在 SQL 层过滤非文本，
  省掉 25% 的无效解压
- 解密快照（`_plain.db`）本身就是 SQLite，直接用标准库查

**没有引入外部数据库**（ES / DuckDB / FTS5）。理由：数据量是 20 万级、
单机单用户，SQLite + 进程内缓存已经够；引入外部依赖会让「解压即用」
这个核心体验变成「先装个服务」。

## 架构

`gui/server.py` 原本是 1521 行的单体，`do_GET` 里 183 行 if 链（26 分支）。

已做的：18 个标准 JSON 端点上路由表，加接口只需加一行；`do_GET` 降到 134 行。
8 个特殊分支（静态文件、SSE、二进制、导出下载）保留在链上——它们要自己管
header，硬抽进表里反而要发明一套 handler 协议。

**没有做的**：把 server.py 拆成多个模块。理由：
- 所有 `api_*` 都是 `run_gui` 的闭包，共享 `_ds_lock` / `_ds` / `tasks` 等状态
- 拆包需要先引入一个「应用上下文」对象，那是几百行的改动
- 当前 1521 行、8 个特殊分支的复杂度，还在一个人能读懂的范围内
- 没有测试保护时拆包=拿稳定性赌收益；现在有 12 例路由契约测试，但还不够

如果将来要拆，顺序应该是：先补更多行为测试 → 引入上下文对象 → 再分包。

## 前端

总计约 380 KB（含 Vue 168 KB），本机加载无压力。**不是瓶颈，未做拆分/懒加载**。

已核验无缺陷的部分：
- 无障碍：6 个主页面，无名按钮 0、无 alt 图 0、无标签输入框 0
- 响应式：1440 / 1100 / 900 / 700 px 均无横向溢出

## 复现方式

```bash
# 接口耗时
for ep in /api/status /api/sessions /api/report; do
  curl -s --noproxy '*' -o /dev/null -w "$ep %{time_total}s\n" "http://127.0.0.1:8788$ep"
done

# 单元测试（482 例）
python -m unittest discover -s tests -q

# 路由契约（需要 GUI 在跑）
python -m unittest discover -s tests -p "test_gui_routes.py"

# 端到端（10 模块 40 步）
python tests/e2e/run_e2e.py
```
