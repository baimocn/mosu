## 二、根因与决策依据

### 朋友圈图片为什么点不开

三层原因叠加，逐层剥开：

1. **地址缺 token**——微信 4.x 把访问凭证放在 `<url token="...">` 属性上，前端把
   裸地址丢给浏览器，既没 token 也没 Referer，必然拉不到。
2. **凭证已过期**——sns.db 是本地快照，实测 1369 张图的 token 全部返回 400；且
   朋友圈 md5 与本地媒体库的交集为 **0**，本机确实没有任何一张图片实体。
3. **无失败态**——原实现 `onImgErr` 直接 `display:none`，用户只看到空白。

对应决策：

- **服务端代抓**而不是让浏览器直连（解决 1），但**只接受 md5 反查**、不接受任意
  URL——否则服务会变成任意网址的代理。
- **提前探测**（解决 3）——页面加载后后台探一次，确认取不到就直接占位并给出补救
  办法，而不是让用户一次次点失败。结果缓存 24 小时，token 过期是不可逆的。
- **把 `cache/` 纳入媒体索引**（解决 2 的补救路径）——用户去微信里重新刷一遍那条
  朋友圈，图片会落到 `user_dir/cache`，此后本地命中。索引从 13457 涨到 15946 张。

### 为什么不是「所有板块」都要改

本项目只有两个出现图片的地方：**聊天记录**和**朋友圈**。没有独立的「动态」或
「相册」页面（已 grep 全仓库确认）。所以统一改造的对象是这两个，二者现已共用同一
套灯箱组件与缩略图/原图两档接口。

### 为什么默认角色不是倾听者

logo 按要求定位为「倾听者 / 陪伴式对话助手」，但 `DEFAULT_PERSONA` 仍是 `mimic`
（白墨本人分身）——后者是产品最早的能力，微信通道最初就是以「用你的口气回消息」
为前提建的。

擅自改默认值会改变已有用户的实际行为，这不是我该单方面决定的。已在
`docs/personas.md` 写明关系与改法（改一行常量即可），列为待确认项。

### 为什么修完 8 处 bug 还要写 13 条不变量测试

这 8 处里有 4 处是**静默失效**（功能不报错但结果错）：字段名不匹配、星期错位一天、
采样方向反了、`social` 同名合并。没有测试锁住，下一次重构会原样复现。所以把
「星期映射」「insights 不做未计算推断」「采样倒序」「social 用 wxid 作键」写成
断言，而不是只写「这次修好了」。

## 四、遗留风险

### 已知但本轮未修

| 风险 | 影响 | 建议 |
|------|------|------|
| 统计不去重、浏览页去重 | 两页消息总数可能不等 | 下轮统一到 `raw_messages()` 的 `_dedup_key` 口径 |
| 统计接口不接受时间范围 | 只能全量统计 | 接入 `from_ts/to_ts`（core 层已支持，只是没接到 HTTP） |
| `contact_profile` 无耗时上限 | 14 万条大群可能耗时以分钟计、内存数百 MB | 加 `max_msgs` 上限与进度条 |
| `keyword_stats` 持锁数分钟 | 期间所有数据 API 阻塞 | worker 内改成分批释放锁 |
| 群聊画像「我/对方」二分 | 数百成员聚合成一个人 | 需要成员级聚合，是独立特性 |
| 两套 type 词表 | 同一公众号在会话列表与联系人页类型可能不同 | 合并为一套 |
| `report()` 首末消息正文是死代码 | GUI 看不到 | 要么返回，要么删 |
| 空库显示一屏 0 | 观感差 | 补空态 |
| 时间分布不补零 | 凌晨无消息的小时在图上缺失 | 后端补全 24 桶 |
| `MediaStore.files` 按原文件名索引 | 同名文件会互相覆盖 | 改为按 hash 或路径索引 |
